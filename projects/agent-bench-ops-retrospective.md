> AgentBenchOps 是一个可观测、可恢复、可通过 HTTP 控制的工具调用 Agent 评测平台。  
> 这个项目真正想解决的，不是“怎样让 Agent 调用一个工具”，而是：**当 Agent 开始读取和修改真实状态时，怎样证明它做对了，并在出错后安全地继续。**

## 项目概览

AgentBenchOps 将 Benchmark 任务、Agent Runtime、工具调用账本、Checkpoint、评测结果和平台 API 串成一条可以追踪的执行链。

项目目前使用的主要技术包括：

`Python 3.13` · `FastAPI` · `LangGraph` · `PostgreSQL` · `Redis` · `SQLAlchemy` · `Alembic` · `Docker Compose` · `GitHub Actions`

最终形成的核心能力包括：

- 使用 YAML 定义和版本化 Benchmark 任务；
- 运行基于 LangGraph 的工具调用 Agent；
- 将运行、步骤、工具操作和评测结果持久化；
- 同时检查最终业务状态和 Agent 的执行轨迹；
- 为外部副作用提供幂等账本和未知状态处理；
- 使用 PostgreSQL Checkpoint 暂停和恢复 Run；
- 通过 HTTP API 提交实验、查询状态和恢复任务；
- 使用独立 Worker、租约和心跳执行持久化任务；
- 输出经过脱敏的结构化事件与低基数指标；
- 使用数据库迁移、自动化测试和容器安全配置约束发布质量。

2026 年 7 月，项目完成了 `1.0.0` 阶段。对我来说，“完成”并不是指它已经可以直接作为商业平台上线，而是指最初设定的核心闭环已经成立：**任务能够被定义、执行、记录、评估、暂停、恢复和通过 API 管理。**

## 为什么要做这个项目

很多 Agent 示例的主流程大致是：

```text
用户提出问题
→ 模型决定调用工具
→ 工具返回结果
→ 模型生成最终回答
```

这种 Demo 很适合说明模型会不会使用工具，但一旦工具开始修改数据库或外部系统，问题就复杂了。

例如，一个 Agent 接到“为某位员工创建服务工单”的任务。最终回答可能是：

```text
工单已经创建完成。
```

但这句话本身无法证明：

- 工单是否真的写入数据库；
- 写入的目标员工是否正确；
- 是否重复创建了两张工单；
- Agent 是否调用了未授权工具；
- 工具超时后，外部系统是否其实已经成功；
- 进程中断后，再次执行会不会重复产生副作用；
- Agent 是否在得到结果前就提前宣称成功。

我逐渐意识到，Agent 的可靠性不能只通过最终自然语言判断。真正需要评测的是：

1. **最终状态是否正确；**
2. **执行过程是否合法；**
3. **资源使用是否在预算内；**
4. **发生中断时能否恢复；**
5. **副作用是否可以审计和去重。**

因此，AgentBenchOps 从一开始就不是一个聊天页面，也不是一个单纯的 Prompt 实验，而是一个以执行可靠性为中心的评测与运行平台。

## 我选择的业务场景

为了避免一开始就陷入“支持所有工具、所有模型、所有业务”的范围失控，我选择了一个简化的企业账号与服务工单系统作为 MVP 业务域。

它包含：

- 员工；
- 账号；
- 权限定义；
- 员工与权限关系；
- 服务工单。

典型任务包括：

- 查询员工和账号状态；
- 查看员工权限；
- 创建或更新服务工单；
- 申请或撤销权限；
- 处理账号恢复；
- 验证审批和操作顺序。

这个场景不算华丽，但它非常适合暴露 Agent 工程中的真实问题：权限、写操作、并发更新、幂等、审批、失败恢复和状态验证都可以在一个相对可控的业务域中出现。

这也是我在项目范围上的第一个重要取舍：

> **先把一个业务域做深、做完整，再讨论扩展性，而不是先做一个看起来什么都支持、实际上没有可靠性边界的框架。**

## 系统架构

项目当前可以简化为下面这条链路：

```text
                         ┌────────────────────┐
                         │   Benchmark YAML   │
                         │  任务、初始状态、规则 │
                         └─────────┬──────────┘
                                   │ 导入与校验
                                   ▼
┌──────────┐    HTTP     ┌────────────────────┐
│  Client  │ ──────────→ │    FastAPI API     │
└──────────┘              │ 认证、计划校验、入队  │
                          └─────────┬──────────┘
                                    │ 创建持久化任务
                                    ▼
                          ┌────────────────────┐
                          │     PostgreSQL     │
                          │ Job / Run / Step   │
                          │ Ledger / Evaluation│
                          │ Checkpoint         │
                          └─────────┬──────────┘
                                    │ 领取、续租、心跳
                                    ▼
                          ┌────────────────────┐
                          │   Worker Process   │
                          │ Benchmark Runner   │
                          └─────────┬──────────┘
                                    │
                                    ▼
                          ┌────────────────────┐
                          │  LangGraph Runtime │
                          │ Model ↔ Tool Loop  │
                          └──────┬───────┬─────┘
                                 │       │
                          工具调用│       │事件与指标
                                 ▼       ▼
                    ┌────────────────┐  ┌────────────────┐
                    │ Tool Gateway   │  │ Observability  │
                    │权限、账本、幂等 │  │日志、脱敏、指标 │
                    └───────┬────────┘  └────────────────┘
                            │
                            ▼
                    ┌────────────────┐
                    │ Business State │
                    │员工、账号、权限 │
                    │工单等业务数据   │
                    └───────┬────────┘
                            │
                            ▼
                    ┌────────────────┐
                    │   Evaluation   │
                    │State / Trace   │
                    │Temporal/Budget │
                    └────────────────┘
```

API 不直接在请求进程里完成整个实验，而是创建 PostgreSQL 持久化执行任务并返回任务标识。独立 Worker 领取任务、维护租约和心跳，再执行 Benchmark。

这种拆分比“API 收到请求后直接跑 Agent”复杂，但它解决了几个实际问题：

- HTTP 请求不需要一直占用到实验结束；
- API 进程和执行进程可以分别管理；
- 任务不会只存在于进程内存中；
- Worker 异常退出后，可以根据租约判断任务状态；
- 执行状态能够被外部客户端持续查询。

## 核心设计一：不只评最终回答

项目中最重要的设计之一，是同时维护多种评测视角。

### State Oracle

State Oracle 检查最终业务状态是否符合预期。

例如创建工单任务完成后，它会检查：

- 目标工单是否存在；
- 请求人和目标员工是否正确；
- 标题、描述、风险等级和状态是否正确；
- 是否出现不应该存在的额外数据。

### Trace Oracle

Trace Oracle 检查 Agent 的工具调用轨迹。

它关注：

- 必须调用的工具是否出现；
- 禁止调用的工具是否被使用；
- 调用次数是否符合要求；
- 工具调用参数是否满足规则；
- 执行过程中是否出现安全违规。

### Temporal Oracle

仅仅调用了正确工具还不够，调用顺序也可能决定任务是否正确。

例如：

```text
先检查权限 → 再执行高风险操作
```

和：

```text
先执行高风险操作 → 再补一次权限检查
```

从最终状态上可能看不出差别，但安全含义完全不同。Temporal Oracle 用来检查这些时序约束。

### Budget Oracle

Agent 还需要受到资源预算约束，例如：

- 最大步骤数；
- 最大工具调用数；
- Token 预算；
- 时间预算。

这样，一个“最终做对了，但绕了几十步、重复调用大量工具”的 Run 不会与一个稳定、直接的 Run 得到相同评价。

这部分让我真正理解到：

> **Agent 评测不是给最终回复打一个主观分数，而是为状态、行为、顺序和资源建立可以执行的规则。**

## 核心设计二：工具调用必须有账本

Agent 调用只读工具时，失败通常比较容易处理；但写工具会产生外部副作用。

以创建工单为例，可能出现下面的情况：

```text
Agent 发起 create_ticket
→ 数据库已经成功提交
→ 网络连接在返回响应前中断
→ Agent 看到超时
```

此时系统无法简单地判断“失败”。如果直接重试，可能创建第二张工单；如果直接当作成功，又可能掩盖真正的失败。

因此，AgentBenchOps 为工具调用建立了独立的操作账本，记录：

- `operation_id`；
- `run_id` 和步骤；
- 工具名称；
- 规范化参数及参数摘要；
- 幂等键；
- 风险等级与审批要求；
- 当前状态；
- 重试和恢复次数；
- 结果摘要；
- 延迟；
- 外部引用；
- 错误和恢复信息。

工具状态不仅包含 `succeeded` 和 `failed`，还包含 `prepared`、`running`、`unknown`、`rejected`、`cancelled` 等状态。

其中 `unknown` 很重要。它承认系统在某些时刻确实无法立即判断外部副作用是否成功，而不是为了让状态机看起来整齐，强行把结果归入成功或失败。

参数会先进行稳定的 JSON 规范化，再计算摘要。因此，即使字典键顺序不同，只要参数语义相同，就可以得到一致的参数摘要。数据库唯一约束和幂等键则用于阻止同一个 Run 重复执行同一写操作。

这个设计让我学到：

> **可靠系统不是永远知道答案，而是能够明确表达自己什么时候不知道，并为之后的核对和恢复留下证据。**

## 核心设计三：暂停和恢复不是重新运行

如果一个 Agent 在执行中被暂停，最粗糙的恢复方式是从头重新运行。但对带副作用的任务来说，这通常不安全。

AgentBenchOps 使用 PostgreSQL Checkpoint 保存 LangGraph 执行状态。恢复 Run 时，系统会检查：

- Run 是否存在；
- 数据库状态是否仍允许恢复；
- 是否确实处于暂停状态；
- 是否存在合法的待执行节点；
- Checkpoint 是否存在；
- 持久化的模型身份是否在允许范围内；
- 是否已经有其他恢复操作占有执行权。

恢复操作会原子声明恢复权，并从已有 Checkpoint 继续，而不是重新执行整个任务。

项目还使用数据库行锁、恢复状态标记和全局 advisory lock，避免两个请求同时恢复同一个 Run，或者执行和恢复同时修改业务状态。

这里最困难的并不是“把状态保存下来”，而是定义清楚：

- 哪些状态可以恢复；
- 谁拥有恢复权；
- 恢复后从哪个节点继续；
- 哪些工具调用不能再次发生；
- 恢复到终态后，评测应该读取哪个时刻的状态。

最终，我把“可恢复”理解为一种端到端语义，而不是一个 `resume()` 函数。

---

## 核心设计四：评测必须捕获正确时刻的状态

项目开发过程中，一个很容易忽略的问题是：Benchmark 运行结束后，业务状态可能会被重置，为下一次实验准备初始环境。

如果评测发生在重置之后，即使 Agent 做对了，State Oracle 看到的也会是初始状态。

因此，首次评测必须在业务状态重置前完成，并显式使用当前 live state。持久化后的重评估则可以读取已经保存的状态来源。

这看起来像一个实现细节，实际上决定了评测结果是否可信。

它也让我意识到，运行和评测不能被当成两个完全独立的模块。评测需要理解状态的生命周期，而执行引擎也必须为评测保留正确的观察点。

---

## 核心设计五：可观测性不能改变业务结果

项目输出结构化事件，并通过上下文关联：

- `experiment_id`；
- `run_id`；
- `trace_id`；
- `task_id`；
- `checkpoint_ref`；
- `operation_id`；
- 组件名称。

同时，敏感字段和原始负载会在输出前脱敏。

指标实现只允许固定的低基数标签，例如组件、事件名称、状态、工具名称和评测来源。`run_id`、`trace_id` 等高基数字段不会进入标签，避免指标维度无限增长。

更重要的一条约束是：

> **日志、指标或可选观测组件发生故障时，不得改变 Agent 执行、工具副作用、账本终态或评测结果。**

可观测性是为了理解系统，而不是成为新的业务故障源。这个原则也影响了事件输出、异常处理和 stdout/stderr 的分离方式。

## 核心设计六：API 的安全边界

平台 API 将只读查询与状态修改接口分开处理。

修改状态的接口需要 Bearer API Key；如果服务端没有配置有效密钥，写接口会直接拒绝请求，而不是为了方便开发自动放行。

API 对外返回的 Run 信息也经过筛选。响应可以包含运行状态、模型身份、步骤数、工具调用数、Token、延迟和评测结果，但不会直接暴露：

- Checkpoint 内容；
- 原始消息历史；
- 工具参数和完整输出；
- 内部配置；
- 凭证；
- 原始异常文本。

此外，生产环境配置会拒绝调试模式、不安全密钥以及不合适的本机依赖地址。

这些限制会让开发过程多一些工作，但它们把项目从“本地脚本”推向了一个具有明确边界的平台。

## 从原型到 1.0.0

整个项目大致经历了以下阶段。

### 1. 先确定评测对象

我没有先写 Agent 图，而是先定义：

- 什么是正确状态；
- 什么是合法轨迹；
- 哪些行为必须出现；
- 哪些行为禁止出现；
- 如何限制步骤、工具、Token 和时间预算。

### 2. 建立业务状态与平台数据模型

业务表负责员工、账号、权限和工单；平台表负责：

- Benchmark 任务；
- Agent Run；
- Run Step；
- Tool Operation；
- Approval；
- Evaluation Result；
- Execution Job。

数据库结构使用 Alembic 迁移管理，并检查模型与迁移是否发生漂移。

### 3. 将 Benchmark 数据化

任务通过 YAML 描述，包括：

- 任务身份与版本；
- 用户请求；
- 初始业务状态；
- 可用工具；
- 预期最终状态；
- 必须和禁止出现的事件；
- 时序规则；
- 预算；
- 元数据。

Pydantic 模式负责拒绝未知字段、重复标识、非法引用和不一致配置。

### 4. 建立工具网关和操作账本

工具注册表、权限检查、业务权限、参数与结果模式、风险等级、审批和幂等逻辑被集中到工具层，而不是散落在各个 Agent 节点里。

### 5. 接入 LangGraph 与 Checkpoint

Agent 运行状态、模型调用、工具调用和暂停恢复被放入显式执行图中，并通过 PostgreSQL Checkpoint 保存。

### 6. 建立多维评测

State、Trace、Temporal 和 Budget Oracle 共同形成评测结果，而不是依赖最终文本相似度。

### 7. 平台化

FastAPI 提供计划校验、实验提交、任务查询、Run 查询、Evaluation 查询和恢复接口。

实验提交从同步请求内执行，演进为：

```text
API 接收请求
→ 创建 PostgreSQL 持久化 Job
→ 返回 202 Accepted
→ Worker 异步领取并执行
→ 客户端查询状态
```

### 8. 补齐运维与发布边界

最后加入了：

- Worker 心跳和租约；
- readiness 与 liveness；
- 数据库迁移与备份流程；
- 密钥轮换说明；
- 非 root 容器；
- 只读根文件系统；
- capability 删除；
- `no-new-privileges`；
- PID 限制；
- GitHub Actions 质量门禁。

这一阶段让我看到，一个项目真正接近“可交付”，往往不是因为又增加了一个功能，而是因为失败处理、部署、迁移和文档终于形成了闭环。

## 我遇到的几个具体问题

### Windows 异步事件循环兼容性

Psycopg 异步模式不支持 Windows 默认的 Proactor Event Loop。项目因此提供独立的服务器入口，在 Windows 中切换到 Selector Event Loop，而不是要求使用者记住每次手动配置。

这件事提醒我：跨平台支持不能只写在 README 里，它应该尽可能进入程序入口和自动检查。

### Pydantic 对象与 JSONB

Benchmark 初始状态最初以 Pydantic 对象存在，直接写入 PostgreSQL JSONB 时会失败。最终统一通过 JSON 模式的 `model_dump` 转换成可持久化数据。

这个问题看似简单，却让我更重视领域对象、传输对象和持久化对象之间的边界。

### 异步执行与文档同步

项目从请求内同步执行演进到持久化 Job 和独立 Worker 后，API 行为、状态码、查询方式、部署结构和故障处理都发生了变化。

代码改完并不代表迁移完成。README、API 文档、运维手册、示例命令和 Changelog 都必须同步更新。否则系统虽然可以运行，使用者得到的却是相互矛盾的事实。

### Worker 消失后的处理

Worker 在执行任务时可能意外退出。系统不能简单地自动重跑，因为先前的工具可能已经产生外部副作用。

因此，租约过期后任务会进入明确的失败状态，而不是盲目自动执行。重新运行前，需要检查工具账本中是否存在 `unknown`，以及是否需要先恢复外部状态。

这是一种偏保守的策略，但相比“看起来很自动、实际上可能重复写入”，我更愿意让系统先停下来并留下可检查的证据。

## 如何验证项目不是“只能在我的电脑运行”

项目的质量门禁包括：

```text
ruff check app tests scripts
python -m pytest
alembic check
git diff --check
```

CI 还会检查：

- 数据库迁移可以应用；
- SQLAlchemy 模型与 Alembic 迁移不存在漂移；
- Docker Compose 配置有效；
- 镜像默认入口正确；
- 迁移文件被正确打包；
- 应用镜像使用非 root 用户；
- Worker 能在只读根文件系统、无 Linux capabilities 的容器中启动。

项目同时提供：

```text
GET /health/live
GET /health/ready
```

`live` 用于判断进程是否存活，`ready` 会检查 PostgreSQL 和 Redis 是否可用。依赖故障时，服务可以继续保持存活，但停止接收需要依赖的工作。

我没有把“测试通过”写成一个抽象口号，而是尽量让代码、数据库、容器和运行环境都进入验证范围。

## 项目当前的边界

我不希望复盘只写成功，也需要说明它目前没有解决什么。

### 1. 受控 API 使用固定模型

当前执行 API 使用代码内的 Scripted Benchmark 模型。调用方不能通过请求任意指定模型供应商、模型地址、凭证或自定义 Runtime。

这降低了远程代码和凭证注入风险，也让平台行为更可重复，但还不是一个通用模型评测服务。

### 2. Compose 不是公网生产部署方案

仓库内的 Docker Compose 主要用于：

- 本地开发；
- 集成测试；
- 单机验证；
- 发布前冒烟测试。

正式环境仍需要 TLS、受控网络、集中密钥管理、远程数据库、可靠备份和更完整的部署平台。

### 3. 并发能力仍然保守

Benchmark Runtime 当前采用串行约束，实验执行和 Run 恢复共享数据库全局锁。

这种设计优先保证状态与评测一致性，但限制了吞吐量。未来要支持高并发，需要进一步拆分业务状态隔离、执行锁粒度和 Worker 调度模型。

### 4. 指标仍是进程内状态

当前指标实现不依赖 Prometheus 或 OpenTelemetry Collector，适合验证事件和指标设计，但不是持久化监控系统，也没有默认公开 HTTP 指标端点。

### 5. 认证仍然简单

当前写 API 使用单个静态 Bearer Key，没有双密钥重叠轮换窗口，也没有多租户、用户角色或细粒度 API 授权。

这些限制不是被隐藏的“以后再说”，而是当前版本明确的边界。

## 我从这个项目中学到了什么

### Agent 工程的主体往往是后端工程

模型与工具循环只占系统的一部分。真正消耗大量设计工作的，是状态、幂等、事务、锁、恢复、权限、评测、迁移和观测。

当 Agent 可以修改外部世界时，它首先是一个分布式系统参与者，然后才是一个会生成文本的模型。

### “失败”不是一个状态

工具超时、Worker 消失、数据库提交后响应丢失、Checkpoint 缺失、重复恢复请求，这些失败的含义完全不同。

可靠性设计需要把失败拆开，并为每类失败定义可验证的后续行为。

### 评测必须与系统一起设计

如果项目先把 Agent 做完，最后再补评测，往往只能检查最终回答。

当 State、Trace、Temporal 和 Budget Oracle 从一开始进入任务模式，运行过程才会留下足够的信息供评测使用。

### 数据库约束比代码注释更可靠

幂等键、唯一约束、行锁、迁移和状态约束把很多“不应该发生”的情况直接封在数据层，而不是依赖每一条调用路径都自觉遵守约定。

### 文档也是系统的一部分

API 文档、运维手册、Changelog 和示例命令并不是项目完成后的装饰。它们迫使我重新检查系统的边界、错误行为和部署假设。

当一个行为无法被清楚写出来时，通常意味着它在代码中也没有被真正定义清楚。

---

## 如果重新开始，我会怎么做

重新做一次，我会更早完成三件事：

1. **先写一条最小端到端任务。**  
   从 YAML、状态重置、Agent、工具账本一直走到 Evaluation，再扩展功能。

2. **更早区分当前事实文档和历史设计文档。**  
   设计快照适合记录演进，但 API 与运维文档必须始终只描述当前版本。

3. **更早建立平台级状态机。**  
   Run、Job、Tool Operation 和 Checkpoint 的状态关系越早明确，后续 API、恢复和错误码越容易保持一致。

但我不会改变最初的核心方向：先解决可验证、可恢复和可审计，再增加更多模型、工具和任务。

## 下一步可能做什么

`1.0.0` 是一个完整阶段，而不是这个方向的终点。后续可以继续探索：

- 可插拔且受控的模型提供方；
- 更丰富的 Benchmark 任务与故障注入；
- Prometheus / OpenTelemetry 等外部观测后端；
- 面向实验、Run 和 Trace 的 Web 控制台；
- 更细粒度的执行锁和多 Worker 调度；
- 多租户认证与权限；
- Benchmark 统计分析和模型对比报告；
- 更系统的安全与恢复任务集。

不过在继续添加功能之前，我更希望先让现有设计经得起阅读、运行和质疑。

## 结语

AgentBenchOps 最初看起来是一个 Agent 项目，但做到后面，它更像是一次后端可靠性练习。

我真正完成的，不只是一个会调用工具的 Agent，而是一套围绕它的约束：

```text
任务有版本
状态可重置
操作有账本
副作用可去重
过程可观察
结果可评测
中断可恢复
接口有边界
部署可检查
```

这个项目也改变了我对 Agent 的理解。

我不再只关心模型能不能在一次演示中给出正确答案，而更关心：当它被放进一个长期运行、会失败、会重试、会修改真实状态的系统之后，我们还能不能相信它。

而 AgentBenchOps，就是我对这个问题给出的第一份完整回答。
